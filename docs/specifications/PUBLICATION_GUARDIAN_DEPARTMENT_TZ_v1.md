# 1. НАЗНАЧЕНИЕ

## 1.1 Цель

`PublicationGuardianDepartment` является обязательным предпубликационным
контуром безопасности Butler Omega Smart.

Отдел обязан проверять состав публикации до передачи данных за пределы
локального доверенного контура и выдавать однозначный машинно-читаемый
вердикт:

- `PASS`;
- `PASS_WITH_WARNINGS`;
- `BLOCK`;
- `FAULT_BLOCK`.

Ни один внешний исполнитель публикации не получает разрешение на продолжение,
если итоговый вердикт отличается от `PASS` или явно разрешённого политикой
`PASS_WITH_WARNINGS`.

## 1.2 Поддерживаемые назначения публикации

Отдел проектируется независимо от конкретного внешнего сервиса и применяется к:

- публичным и частным Git-репозиториям;
- GitHub, GitLab, Gitea, Bitbucket и внутренним Git-серверам;
- релизным ZIP/TAR-пакетам;
- пакетам передачи заказчику;
- внешним файловым хранилищам;
- экспортируемой документации;
- публикации исходного кода, конфигураций и тестовых материалов.

## 1.3 Принцип Fail Closed

При ошибке инициализации, повреждении политики, недоступности источника,
невозможности прочитать публикуемый объект, сбое инспектора или нарушении
целостности Git-репозитория отдел обязан запретить публикацию.

Неопределённость никогда не трактуется как разрешение.

## 1.4 Граница ответственности

Отдел:

- анализирует объект публикации;
- формирует нарушения и предупреждения;
- принимает вердикт;
- формирует неизменяемый отчёт;
- предоставляет инструкции по устранению нарушений.

Отдел не имеет права:

- самостоятельно выполнять `git push`;
- самостоятельно публиковать файлы;
- автоматически удалять или редактировать пользовательские данные;
- автоматически изменять `.gitignore`;
- автоматически снимать файлы с индекса;
- скрывать обнаруженные нарушения;
- обходить собственный вердикт.

# 2. АРХИТЕКТУРНЫЕ ИНВАРИАНТЫ

1. Реализация соответствует действующему Butler Department Standard.
2. Взаимодействие выполняется через формальные входные и выходные контракты.
3. Ядро отдела не содержит логики конкретных инспекторов.
4. Инспекторы подключаются через расширяемый Plugin API.
5. Политики отделены от программного кода.
6. Проверяется фактический объект публикации, а не произвольное дерево проекта.
7. Все текстовые файлы создаются и обрабатываются в UTF-8 без BOM.
8. Секретные значения запрещено записывать в отчёты и журналы полностью.
9. Любое CRITICAL-нарушение безусловно блокирует публикацию.
10. Результат проверки должен быть воспроизводимым для одного состава входных данных.

# 6. ИНСПЕКТОРЫ БЕЗОПАСНОСТИ

## 6.1 Общие требования

Каждый инспектор реализует единый контракт и выполняется независимо
от остальных инспекторов.

Инспектор обязан быть детерминированным.

При одинаковом входе инспектор обязан вернуть одинаковый результат.

Инспектор не имеет права:

- изменять анализируемые файлы;
- изменять Git Index;
- выполнять commit;
- выполнять push;
- изменять политики;
- скрывать нарушения;
- завершать работу других инспекторов.

Каждый инспектор возвращает собственный отчёт.

---

## 6.2 SecretsInspector

Назначение:

Обнаружение секретов любого типа.

Проверяются:

- API Keys
- Bearer Tokens
- OAuth Tokens
- JWT
- SSH Private Keys
- RSA Keys
- OpenAI Keys
- Anthropic Keys
- Gemini Keys
- OpenRouter Keys
- AWS Credentials
- Azure Credentials
- GCP Credentials

Каждое найденное значение классифицируется.

Уровни:

INFO

WARNING

HIGH

CRITICAL

BLOCK

При уровне BLOCK публикация прекращается.

---

## 6.3 PrivacyInspector

Назначение:

Поиск конфиденциальной информации.

Проверяются:

- паспортные данные;
- банковские реквизиты;
- телефоны;
- адреса;
- e-mail;
- персональные документы;
- внутренние документы;
- служебные инструкции;
- данные сотрудников.

---

## 6.4 ConfigurationInspector

Проверяются:

.env

.env.local

.env.production

credentials.*

secret.*

private.*

token.*

password.*

config.local.*

settings.local.*

---

## 6.5 BinaryInspector

Назначение:

Контроль бинарных файлов.

Проверяются:

- исполняемые файлы;
- архивы;
- модели;
- большие бинарные объекты;
- неизвестные форматы.

Инспектор обязан определять:

- MIME;
- расширение;
- размер;
- контрольную сумму.

---

## 6.6 GitInspector

Назначение:

Проверка состава публикации.

Источник проверки:

git diff --cached

Инспектор анализирует только индекс публикации.

Не допускается анализ произвольных файлов вне объекта публикации.

---

## 6.7 PolicyInspector

Назначение:

Проверка соответствия политике публикации.

Проверяются:

- запрещённые пути;
- запрещённые типы файлов;
- обязательные проверки;
- режим публикации;
- совместимость политик.

---

## 6.8 WhitelistInspector

Назначение:

Проверка разрешённых объектов.

Whitelist никогда не отменяет критические нарушения безопасности.

Whitelist может только снизить уровень предупреждения,
но не имеет права разрешить публикацию секрета.

# 10. ПРОИЗВОДИТЕЛЬНОСТЬ

Отдел обязан поддерживать инкрементальную проверку.

Не допускается повторная проверка файлов,
если они не изменились относительно предыдущего запуска
и политика проверки не изменилась.

Разрешается использовать внутренний кэш результатов.

Кэш не должен влиять на корректность проверки.

При любом сомнении используется повторная полная проверка.

# 26. КРИТЕРИИ ЗАПРЕТА ПРИЁМКИ

Приёмка автоматически отклоняется если обнаружено хотя бы одно
из следующих условий.

- секрет опубликован полностью;
- возможен обход инспектора;
- возможно отключение проверки изменением кода;
- нарушен контракт API;
- отсутствует журнал аудита;
- отсутствует отчёт;
- FAIL_CLOSED реализован некорректно;
- Core зависит от конкретного Git-провайдера;
- инспектор изменяет пользовательские файлы;
- публикация продолжается после BLOCK.
